## Requirements

**1. No new hardware access: PASS.**
- Call sites, counted mechanically on the header text of both commits (*observed*): `sfg_r32(` 25 lines in both, `sfg_w32(` 18 lines in both (16 call sites + definition + one comment), `sfg_rx_pop(` 2 in both, `->rd32(` 2, `->wr32(` 1, `->crit(` 4, `->now(` 8 in both. New call sites of `sfg_r32` / `sfg_w32` / `sfg_rx_pop` / `ops->rd32` / `ops->wr32` / `ops->crit`: **none**.
- The four reads of `sfg_poll` are the same four expressions, re-joined with `&&` (P:741-742). The one `ops->now` call that moved: from `sfg_wait` into `sfg_late` (P:772), called from the same place (P:802), once per unsatisfied poll as before.
- The new functions `sfg_stage` (P:838-846), `sfg_stage_name` (P:849-855), `sfg_why_name` (P:858-863), `sfg_diag_lines` (P:867-880) touch only `r->d`, constant tables and the text helpers; `sfg_diag_lines` calls `ops->say` through `sfg_emit`/`sfg_three` (log output, as every other line).
- Glue and the other files of the patch: the patch text before and after the header hunk is byte-identical at both commits (*observed*, sha256 301d9310... and c4bbdbbb... on both sides).
- Dynamic proof (*observed*): I instrumented a copy of the host test so every `rd32`, `wr32`, `now`, `crit` and `say` call is logged with its arguments, and ran the OLD test (506a64b) against the old and the new header: 775288 trace lines, identical except 33 added `fail` lines (11 failing scenarios x 3); 549885 reads, 1439 writes, 223411 counter reads, 196 crit calls on both sides, same order, same values.

Changed functions: `sfg_poll`, `sfg_wait`, `sfg_xfer`, `sfg_set` only.

**3. `sfg_poll` keeps read order, short-circuit and return codes: PASS.**
- *Read from source*: `!a || !b || !c || !d` and `!(a && b && c && d)` evaluate the same reads in the same order and stop at the first failure (P:741-742). `why` is a priority chain unreadable > nack-int > nack-state > int-errs > lose-state > err-status > none (P:743-744); NACK is returned for exactly the two NACK values (P:755), which is the old `(ist & int_nack) || state == NO_ACK` because both sit above every ERROR cause; ERROR for unreadable (P:753) and for the three other causes (P:757), the old second test; else OK. On an unreadable poll the stale `st` words are copied to the diag (initialised memory: `st = { 0, 0, 0 }` in `sfg_xfer`), not used for the result.
- *Observed*: I compiled the old and the new `sfg_poll` into one program and compared them over 61440 inputs (16 INT_STATUS values over the NACK and error bits, 64 TRANS values over every state, 3 ERR values, 2 FIFO values, read failure at none / 1st / 2nd / 3rd / 4th read, diag NULL and set): 0 differences in return code, in the words left in `st`, in the number of reads and in their order (OK 448, NACK 6528, ERROR 54464 cases). In the new one the recorded `why` always agrees with the return code. ASan/UBSan clean.

The first counter read still precedes `sfg_msg_start(r, 0)` (declaration of `t0`, then P:893-894). Write order per outcome is unchanged (*observed*: the trace compare of item 1 covers success, NACK at each message, both timeouts, arbitration, ERR_STATUS, faulting and dropped writes, sticky INT_STATUS). My mutant "sfg_stage returns 0" is killed by the host test.

The mutant "sfg_late never late" is killed by the host test. Text loops of the new lines run in `sfg_txt`/`sfg_hex`, bounded by `SFG_LINE` 200; the longest new line is about 75 characters.

**6. Memory bounds and the NULL case: PASS.**

The pointer does not outlive `sfg_set`. Extra stack: 36 bytes in `sfg_set`, one 204-byte `sfg_buf` in `sfg_diag_lines` (plus `sfg_three`'s, as for the existing lines).
- Tables: `n[SFG_D_NSTAGES]` with 13 initialisers for 13 values, index checked `s < SFG_D_NSTAGES` (P:854); `n[SFG_DW_N]` with 7 for 7, checked `w < SFG_DW_N` (P:862). Largest stage written: `SFG_D_RD_POP0 + 2 * 1` = 10 = `SFG_D_RD_POP1` (P:912, `SFG_VAL_BYTES` 2).

**7. Failure lines print only controller status words: PASS.** Line 1: step name, cause name, ERR_STATUS. Line 2: INT_STATUS, FIFO_STATUS, TRANS_STATUS. All nine `fail at` variants the host scenarios produce were read by me; none carries anything else.

**8. Worst case on the phone.**
